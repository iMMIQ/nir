# M3：准备调度与资源预取

## 范围和工作流

本轮按 M3.0 恢复长尾、M3.1 分阶段调度、M3.2 单 Cue 媒体预取、M3.3 本机长稳推进。三条 GPT-6 Sol / medium effort 工作流分别负责恢复与服务计时、宿主调度、Core／Player 媒体准备；公共配置、集成、浏览器和性能验证由主代理负责。

版本仍为源格式 1、运行时 2、存档 1；新字段默认关闭，旧源文件可继续读取。重建的作品须使用匹配 SDK。Worker、兼容后端、资源 cooking、跨发行存档迁移及多平台正式验收另行推进。

## 作者设置

在独立 player 配置的 `[defaults]` 内设置：

```toml
prefetch_content = true
prefetch_media = false
```

`prefetch_content` 仍只控制确定的后续模块内容获取。`prefetch_media` 独立控制媒体 lookahead，默认关闭；示例显式开启，最小模板保持关闭。这些是作者默认配置，不是玩家偏好或存档状态。

预测最多沿 64 个不同基本块寻找一个确定的后续 Cue，遇到分支、选项、调用、返回、循环或缺失定义停止。不执行表达式、不消耗随机数、不推进剧情。只使用已驻留配方和资源目录，只准备图片和音频；目录缺失或容量不足时跳过。

推测媒体只有一个批次，新增估算成本最多 32 MiB，且受现有 128 MiB 联合媒体账本限制。账本还包含活动资源和固定绘制表面成本；32 MiB 不是额外增加的预算，也不是物理显存限额。正式需求可以提升共享工作并回收失效推测，但仍须完成正常准备和候选提交。

## 调度边界

准备优先级为 Required、Near、Speculative、Background。正式准备优先；下一确定 Cue 属于 Near，原有内容 prefetch 映射为 Speculative。同级有期限任务按期限与近期成本估计排序，无期限任务按入队顺序推进。

下载／校验最多四项并发，音频解码最多两项准入；下载完成后释放网络槽，不占着网络槽等待 owner 上传。同步 PNG 解码仍是原子调用。图像上传每轮最多 2 MiB，并在步骤之间检查时间预算；不能由此推导每个浏览器任务都少于 4 ms。

准备阶段的完成经有界 inbox 交付。完整纹理才能成为可用资源；资源可用不等于剧情提交。取消、代次检查和联合准入仍由 owner 协调，推测准备本身没有剧情激活权限。

## 长稳复现

构建 SDK 和示例发行后：

```sh
NIR_PERF_LONGRUN_SECONDS=7200 bun run test:performance:hardware --trace=off --grep 'M3 sustained'
```

无显示环境设置 `XVFB_RUN`，指定 `CHROMIUM`。短时 CI 使用同一场景、120 秒目标时长。测试覆盖双分支、存读档、回退、语言切换、周期性设备重建及独立多模块路线，每轮返回标题后采集一致的清理状态。

每轮样本追加到 `reports/performance-m3-longrun.json.jsonl`，每分钟及结束时原子更新完整 JSON 报告，失败时保存诊断。这样避免长稳过程中反复重写越来越大的报告。Linux 上读取浏览器进程的 RSS/PSS，并采集 JS 堆、WASM 容量与预算账本；RSS 求和可能重复统计共享页。GPU 分配未取得可靠计数时明确标记未测量，不以预算估算替代。

完整两小时、短时回归和采样中断必须分别报告；未达到目标时长不标记长稳验收通过。实际结果见 [M3 验证](validation/m3/README.md)。
