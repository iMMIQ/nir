# 分块内容与驻留契约

## 发布边界

作者源 `Program` 保持 format 1；发布运行时使用 format 2 的根索引和独立内容对象。新 SDK 和作品必须同步重建。存档仍绑定精确发行身份，不做跨发行迁移。

根索引只携带配置、函数接口、符号归属、文本修订摘要、资源定位和最小标题场景。章节的 Scene、Cue、Choice、TextContract 与资源配方进入静态包；代码、逐语言正文和资源目录分别发布。字体依赖由有效 UI／正文语言计划决定，不再无条件加入每个 Cue。

资源目录按实际消费者集合分组。消费者包括标题、模块和语言字体计划；同一 AssetId 只在一个目录中定义。根资源索引的类型与媒体摘要用于验证引用和字体计划，完整资源描述必须来自经过验证的目录。

## 准备与提交

准备顺序为：解析需求 → 下载内容对象 → 验证并原子安装 → 联合准备旧状态与候选媒体 → 提交。

- 标题启动先解析持久化偏好，再请求所选语言的目录和媒体。
- 执行在缺失内容的指令前暂停；加载不推进剧情时间、随机数或语义 ID。
- 读档覆盖全部调用帧、保留任务、待提交 Cue、选项和冻结对白原语言的正文，以及场景、草稿、转场和音频引用的资源目录。
- 历史记录通过根文本身份摘要验证，不要求加载其原章节正文。冻结对白仍须与原语言正文逐段核对。
- 已实例化任务保存自身 Effect 和冻结对白，正常执行不固定原始定义包；已完成和已取消任务的句柄继续保留。读档仍须逐一验证这些任务的原始定义和对白。
- 网络失败、验证失败和过期请求不能替换已经提交的剧情状态。语言切换失败保留原有效语言。

Host 只消费 Rust 发送的资源描述；WASM 对资源字节继续独立核验。Host 的缓存回收和追踪通过显式 AssetId／对象映射工作，不读取根文件中的完整资源表。

## 内容对象与活动引用

内容键区分模块静态、代码、模块语言文本和资源目录。对象身份由发行根中的 hash 固定。内容正文以不可变 `Arc` 块存储，新对象安装只校验新对象并构建其局部指令索引；既有正文不被复制或重新序列化。

公共接口如下（`nir-format` 定义身份，`nir-content` 负责字节验证，`nir-core` 负责语义与驻留）：

| 接口 | 契约 |
|---|---|
| `ContentKey::{Static, Code, Text, Catalog}` | 同一发行内稳定的逻辑对象键；Text 包含模块和语言 |
| `RuntimeProgram::content_requirement` | 返回键、预期摘要及需求说明 |
| `nir_content::parse_runtime_object` | 限制输入大小、验证摘要、格式、身份和根索引归属 |
| `ValidatedProgram::install_batch` | 只接收已通过字节验证的对象及编码长度；先验证整个候选再返回新视图，失败不修改旧视图 |
| `ValidatedProgram::prepare_install_batch` | 验证需求批次并选择可回收对象，返回尚未提交的 `ContentAdmission` |
| `ValidatedProgram::prepare_prefetch_batch` | 验证预取批次，仅使用剩余额度，不驱逐已有对象 |
| `ContentAdmission::view / commit` | 提交前检查候选视图；提交时同步检查 lease 和驻留代次 |
| `ValidatedProgram::empty_content_view` | 创建同 root、独立账本、无内容正文的恢复校验视图 |
| `RestoreSession::next_requirements / verify_next_unit / finish` | 逐单元验证固定快照，仅全部通过才能产生内部恢复凭据 |
| `Core::restore_verified` | 消费单次凭据，执行剩余完整结构检查后创建恢复候选 |
| `ValidatedProgram::lease` | 仅对驻留键授予不可 Clone 的 `ContentLease`；Drop 释放引用，`info()` 暴露 owner 与键集合 |
| `ValidatedProgram::residency` | 返回预算、唯一 hash 字节计费、每块的键／摘要／编码长度和持有原因 |
| `ValidatedProgram::set_residency_budget` | 返回使用新预算的视图；不能将预算降低到当前驻留量之下 |
| `Player::content_residency` | 暴露播放器当前的驻留与引用状态，供测试和诊断读取 |

Code 和 Text 安装要求同模块 Static 已驻留或在同一批次内；安装时先处理 Static。跨模块调用使用根函数接口；Cue、Choice 和任务定义的语义检查由其所属模块静态包提供。

驻留与引用分开：

- 驻留：对象已经验证并占用内容预算。
- 活动引用：当前调用栈、待提交交互或准备事务仍需要的内容对象；运行任务另保留实际媒体资源。
- 可重载逻辑引用：存档、检查点与历史中的稳定身份；这些引用不永久固定整条阅读路径的内容。

恢复候选与旧状态在提交前并存，各自所需内容及媒体都必须保留。取消候选只释放候选引用；提交后才释放不再需要的旧状态引用。

内容预算统计已安装的 Static／Code／Text／Catalog 包，按唯一对象 hash 的编码字节计费。根索引作为固定基础开销另受单次输入大小限制，媒体继续使用独立资源账本；这些计数不等同于堆内存或浏览器物理内存。单对象／单批次上限为 16 MiB，单批最多 128 个对象；驻留上限初始为 16 MiB。超限在安装提交前明确失败。

M2.2 在需求安装时回收无活动引用的对象，优先回收未使用的预取对象，再按确定性 LRU 选择。Static、Code、Text、Catalog 可独立回收；Static 缺失时，再次执行会先补齐 Static。安装时的语义校验仍要求 Static；缓存中已经校验过的 Code/Text 不因此固定 Static。

驱逐清除对象正文、局部指令索引和派生配方。OpId 所属记录保留，避免先驱逐旧代码再安装冲突代码绕过唯一性检查。事务提交与 lease 注册同步；旧视图不能为已经退休的驻留记录重新获取 lease。外部持有的旧视图可能延长实际 Arc 生命周期，编码字节驻留报告不代表这些外部引用已释放。

## 分批读档校验

恢复分为原始内容校验与候选活动状态准备。恢复会话独占快照，按模块静态定义和冻结对白原始语言逐批获取内容；每批使用同 root 的空内容视图，完成后释放正文，只保留绑定快照、发行和 root 身份的内部校验凭据。全部校验通过后，核心消费凭据并完成结构、continuation、任务进度、场景和根资源身份检查，再准备媒体并提交。

全部旧任务的校验闭包允许超过 16 MiB。内容下载、解析与校验使用独立的 16 MiB 暂存额度；单个 Static 加对应语言 Text 的校验单元必须能容纳。已安装内容另受 16 MiB 限制，恢复期间旧状态与候选的活动集合必须同时容纳。单元或活动集合超限均明确失败，并保留旧剧情。

取消恢复后拒绝迟到批次，网络失败重试当前批次。设备丢失只要求重新准备 GPU 资源；用户偏好变化在最终候选准备时采用最新值，冻结对白的原语言不变。历史和检查点仍只持有可重新解析的逻辑身份。

## 下一模块预取

作者配置 `player.defaults.prefetch_content` 默认开启，不属于用户 Preferences。Story 稳定等待时只读扫描最多 64 个 block，沿 Goto、Activate.next、Await.next 正常成功路径寻找首个跨模块 Call；遇到分支、选项、同模块调用、循环、返回或结束即停止。扫描不执行表达式、不修改状态或随机数。

最多预取一个目标模块缺失的 Static、Code、当前语言 Text；不预取标题后的剧情或媒体。最多一个预取请求，编码字节上限为缓存空闲额度与 2 MiB 的较小值。Host 根据发行清单在下载前检查大小，预取不驱逐缓存；失败或超限跳过不打断剧情。

执行到相同对象集合时提升原请求为必需请求，复用下载；不同需求、读档、返回标题或正文语言变化取消失效预取。必需请求优先于预取，按 hash 合并下载及最后消费者取消仍生效。预算跳过结果与请求提升发生竞态时转为正常需求重试。

## 验收要求

必须验证：有活动引用的对象不能驱逐；无活动引用的代码／静态／文本／目录可独立回收；回退或读档重新准备必要闭包；联合准备失败保留旧状态；长时间跨章节运行的驻留成本受预算约束。物理内存测量应另外报告，不从编码字节账本推算。

## 批次下载与传输表示

宿主对一个内容批次使用最多四个下载 worker，与媒体任务共用全局四槽资源池。相同 hash 去重，结果按请求顺序一次交付；网络完成顺序不改变安装顺序。返回标题时保留上一画面及其纹理，等待标题媒体准备完成再绘制、回收；历史、滚动及对白 Gate 在准备期间仍可更新布局。排队的 required 优先于 prefetch；精确批次提升会提升已排队任务，后续 worker 读取新的优先级。

一个尝试失败时取消同尝试的消费者，并等待全部 worker 结束后才重试或释放 staging。共享下载仍由各自消费者拥有，取消一个批次不会取消另一个批次的需求。预取失败后被正式需求接管时保留已成功对象，其余对象在新尝试中加载。

HTTP gzip 只是传输表示。清单 bytes、内容驻留和 staging 始终统计解压后的对象编码字节，不使用压缩传输量缩减预算计费。发行、运行时和存档格式版本不变。

准备事务暂停音频时，音频字节解码与资源准入不等待 `AudioContext.resume()` 完成；暂停可能使该 promise 延后到准备结束才完成，等待它会形成循环。实际播放恢复仍由原有的音频暂停／恢复命令驱动。

正式需求优先使用空闲 staging。只有容量不足时才回收仍在下载的预取；被回收的请求在消费者全部结束后返回 `E_PREFETCH_LIMIT`，不能只在宿主取消而让 Rust 继续等待。若此时 Rust 已提升原请求，沿原有跳过协议重新发出正式请求。已经排队交付的批次正常完成，不与回收争用同一终态槽。
